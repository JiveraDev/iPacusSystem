# Activity-diagram review: all user roles

Review date: **19 October 2026**. Basis: the current working tree, including existing uncommitted implementation changes. The role names and current destinations were checked in [Dashboard](../../src/components/Dashboard.jsx), [dashboard routing](../../src/components/dashboardRouter.jsx), and the [PHP role policy](../../php/role_access.php). The application has four effective authenticated roles: **Pet Owner, Admin, Veterinarian, and Super Admin**. Staff positions such as Assistant Vet, Secretary, Staff, and HR belong to Admin profiles; they are not additional independent login roles.

The supplied operational bookings/POS/boarding diagram belongs to **Admin**. The supplied personnel/reports/payment-settings diagram belongs to **Super Admin**. The revised files use those labels consistently.

## Boundaries retained in the revision

These diagrams describe implemented connections under their required deployment/configuration. They are not a statement that the configured database, mail service, Google callback, camera/video service, private storage, or backup tooling was exercised successfully today. Missing migrations can block features. Notifications are attempted after successful writes; their delivery is not assumed.

Current menus and frontend role arrays are not the final authority for data access. PHP route, ownership, assignment, and branch checks remain relevant. Existing dashboard/router bypass code was only read.

The review does not certify complete branch isolation. In particular, the current intake handler checks Admin branch access for writes, while its GET query lacks an equivalent Admin branch predicate. That existing limitation is not represented as a successfully enforced universal read gate. Optional Admin feature permissions also retain the existing legacy-default behavior when the permission table/lookup is unavailable.

Quiet GET refresh and local error recovery are shared behavior rather than extra business branches on every role diagram. A timeout or unreadable write response may have an uncertain outcome: refresh the affected record before resubmitting. See [error isolation](../../docs/error_isolation.md), [API client](../../src/services/apiClient.js), and [auto-refresh hook](../../src/hooks/useAutoRefresh.js).
